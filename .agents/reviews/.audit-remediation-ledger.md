## Capstone round 1 — 1 medium, a real cross-cutting gap the whole-diff view surfaced

`GIT_BIN="$(command -v git)"` appears in 6 places (5 SKILL.md sites already reordered for CSR-004,
plus `scripts/lib/git-safe.sh`'s own shared production resolver) — none of them verify the result
is actually an absolute path, exactly the same class of gap Group C already found and fixed for
`CLAUDE_BIN` in `run-ccs-ci.sh`, just never extended to `GIT_BIN`. Reviewer reproduced directly: an
exported Bash function named `git` makes `command -v git` return a bare name (not a path), which
the sanitization loop then runs instead of a real binary, silently skipping sanitization entirely
(the function can return success while doing nothing, so the `|| printf ...` fallback list never
triggers) — a hostile `GIT_DIR` then leaks into the eventual `codex exec` subprocess, since
`run-ccs-review.sh`'s own dispatch subshell only `cd`s to CWD, it doesn't re-sanitize before
invoking `codex`. Also reproduced separately: a relative-PATH-resolved `git` executes a decoy even
under `git-safe.sh`'s own `env -i` isolation (that isolation controls the environment `git` runs
IN, not whether the resolved PATH TO git itself was absolute). `git-safe.sh` (production code) is
the more serious of the 6 instances; the existing regression test only covers a hostile-PATH-before-
sourcing scenario, never a shell-function or relative-path resolution, so it never would have caught
this class of gap. Sent to `audit-fix-c` (natural owner of this exact area).

**Fix applied (commit da02f5e) — verified independently.** Read the diff directly: `git-safe.sh`
gained a `case "$GIT_BIN" in /*) ;; *) ... ;; esac` guard emitting a well-formed `bad_args` JSON
response; all 5 SKILL.md sites gained the same guard using the file's own "echo to stderr, exit 1"
